# Pikafish-jieqi_old 揭棋 AI 分析

## 总体结论

该项目是 Pikafish/Stockfish 框架改造而来的 UCI 揭棋引擎。搜索与剪枝基础较强，暗子处理采用“枚举可能翻出棋型 + 加权期望 + 风险截断”的启发式方法；但它目前更接近确定性近似搜索，而不是严格的暗棋信息集博弈搜索。暗子规则一致性、剩余棋池更新、评估初始化和评估强度仍有明显改进空间。

## 架构与入口

- 编译产物为 `PikaJieQi`，默认揭棋开局和 FEN 解析位于 `src/uci.cpp:44`。
- 引擎保留 Stockfish/Pikafish 的迭代加深、多线程、置换表、空着搜索、LMR、ProbCut、quiescence search 等机制，核心搜索在 `src/search.cpp:580`。
- UCI 协议有扩展：走法可以带第 5 或第 6 个字符，用于表示翻出的棋子和被吃的暗子。

## 棋盘与暗子表示

- FEN 中使用 `x/X` 表示黑/白暗子，例如默认局面位于 `src/uci.cpp:45`。
- FEN 第三段维护双方剩余未翻开的棋子池，由 `src/misc.h:198` 的 `RestList` 管理。
- `Piece` 编码额外使用了暗子位，`src/position.cpp:118` 解析 FEN 时会生成暗子棋盘状态。
- `Position::fen()` 会把剩余棋池重新输出到 FEN，见 `src/position.cpp:321`。

## 暗子搜索机制

1. 搜索过程中移动暗子后，`Position::do_move()` 设置 `darkSquare`、`darkDepth`、`darkTypes` 等状态。
2. `Position::getDark()` 从当前行动方的剩余棋池中逐个取出可能的棋型，替换到刚移动的目标格，见 `src/position.cpp:546`。
3. 每个可能棋型都会作为子分支递归搜索，主搜索在 `src/search.cpp:1309`，quiescence 搜索也在 `src/search.cpp:1854` 使用同样机制。
4. `ScoreCalc` 汇总各棋型分支的返回值：
   - 按剩余同型棋子数量做加权平均；
   - 分值会截断到 `[-DARKVALRATE, DARKVALRATE]`；
   - 若平均值与最差值的差距超过 `DARKMAXDIFF`，则采用最差分值，避免对极端好结果过度乐观。
5. 暗子递归深度受 `MAXDARKDEPTH=4` 和 `MAXDARKTYPES=43` 控制，超过限制后降低搜索深度，定义见 `src/position.h:38`。

## 评估系统

- 当前 NNUE 实际被关闭：`USE_NNUEEVAL=0` 位于 `src/types.h:106`。
- 实际评估使用手工子力、PSQT、威胁、空间、机动性等传统项，入口为 `src/evaluate.cpp:492`。
- 暗子的静态子力用剩余棋池平均值估计；吃掉暗子时还会额外加约 `75` 的收益，见 `src/position.cpp:713`。
- 暗子位置有专用 `PSQT::psqCap` 表，见 `src/psqt.cpp:129`。
- 评估还包含针对暗兵、暗车、暗炮等的威胁修正，见 `src/evaluate.cpp:299`。

## 主要问题与风险

### 1. 暗子信息可能泄露

暗子在棋盘上仍保留按初始格推断出的“名义棋型”，走法生成和攻击判断会使用这个棋型。如果实际揭棋规则中暗子真实身份是随机的，这会导致搜索泄露或依赖不可知信息。

同时，`getDark()` 枚举的棋型是移动后再替换的；它没有验证替换后的棋型是否能从原格合法走到目标格，因此可能搜索到不符合真实规则的翻面子分支。

### 2. 剩余棋池更新不完整

普通搜索生成的暗子吃子走法没有携带 `capPiece`，因此被吃的暗子不会从对方剩余棋池中移除。这会让后续翻子概率和子力估值产生偏差。

相关代码：

- 暗子被吃时只调整估值：`src/position.cpp:713`
- 只有 UCI 扩展走法中的 `capPiece` 才会扣棋池：`src/position.cpp:727`

### 3. NNUE 被关闭，README 描述与实际不一致

项目 README 强调 Pikafish 使用 NNUE 评估，但当前源码中 `USE_NNUEEVAL=0`，NNUE 代码虽然保留并被编译，评估入口实际走传统手工评估。README 的 NNUE 强度描述不适用于当前配置。

### 4. 黑白暗子威胁评估不对称

`Evaluation::initialize()` 每次都会清空 `DarkPieces`。主评估先初始化白方，再初始化黑方，因此第二次初始化会清掉第一次的结果，导致白方暗子威胁信息丢失。相关代码：

- `src/evaluate.cpp:219`
- `src/evaluate.cpp:461`

### 5. 搜索不是严格的信息集博弈搜索

当前方法把一个暗子动作展开成多个“假设翻出棋型”的分支，然后聚合成一个期望值。这个方法能控制搜索成本，但存在两个理论问题：

- 不同玩家掌握的信息不同，普通期望极大化不一定安全；
- 对所有确定性结果取平均后，再进入 minimax 搜索，不能保证等价于信息集层面的 minimax。

因此它更适合视为强启发式，而不是精确的暗棋博弈解。

## 其他观察

- `Position::attackers_to()` 中仍有“暗士”相关 TODO，见 `src/position.cpp:412`。
- `chased()` 也有暗子作为攻击子的规则 TODO，见 `src/position.cpp:1115`。
- `tests/` 下的脚本仍是旧的国际象棋测试，引用 `./stockfish` 和国际象棋 FEN，不能覆盖揭棋逻辑。

## 优先改进建议

1. **修正暗子走法一致性**：枚举候选棋型时，应先检查该棋型能否从原格合法走到目标格。
2. **修复暗子池扣除**：吃掉暗子后必须从对方剩余棋池中移除对应棋型，或重新设计棋池状态。
3. **修复评估初始化**：让黑白双方暗子威胁信息都能保留，避免第二次初始化清空第一次结果。
4. **重新设计信息集搜索**：可考虑在暗子动作处使用机会节点、information-set search、root sampling，或对每个信息集做保守 minimax。
5. **训练揭棋专用 NNUE**：如果目标是强度，应恢复或启用 NNUE，并用揭棋自对弈数据训练；当前手工评估可能是主要瓶颈。
6. **增加揭棋回归测试**：包括暗子 perft、翻子分支数、吃暗子后的棋池数量、重复局面和 UCI 扩展走法解析。
